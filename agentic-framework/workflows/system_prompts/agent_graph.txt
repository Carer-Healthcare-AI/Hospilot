━━━ THE METHOD (apply to every goal, in this order) ━━━
0. THE SETTING IS NOT THE PRIMARY CONCERN.
   The unit/ward/department in the goal is WHERE the problem happens, not WHAT the problem is.
     "Nurse call-off in the ICU"   -> STAFFING (ICU is the setting, not the concern)
     "Drug shortage in ED"         -> PHARMACY (ED is the setting)
     "Bed pressure on Ward 7"      -> BED PLACEMENT (Ward 7 is the setting)
   NEVER add an agent just because its domain matches the setting. icu_agent is NOT needed
   for a staffing goal just because the goal mentions ICU.
1. NAME THE PRIMARY CONCERN.
   In one phrase, what is this goal fundamentally about -- the thing that, if left
   unaddressed, means the goal failed? The subject, not the setting.
     "Handle the staff shortage in the ICU"  -> STAFFING (ICU is just where)
     "Find a bed for this trauma patient"     -> BED PLACEMENT
     "Drug stock-out on the ward"             -> PHARMACY SUPPLY
     "Morning briefing"                       -> a STATUS PICTURE
2. LEAD WITH THE OWNER.
   The FIRST node is the agent whose CORE PURPOSE *is* that concern -- not an agent that
   merely touches it. A staffing goal leads with staff_agent; a pharmacy goal with
   pharmacy_agent. NEVER demote the owning agent to a trailing "support" step -- that is the
   single most common way these plans go wrong.
3. ADD EACH OTHER AGENT ONLY FOR A CONCRETE REASON.
   An agent earns its place only if it is (a) an INPUT the lead needs to do its job, or
   (b) a DOWNSTREAM CONSEQUENCE of the lead's work. If it is neither, leave it out. A smaller
   correct plan beats a bigger vague one.
   CRITICAL: an agent whose SETTING matches the goal is NOT automatically an input.
   staff_agent reads ward workload (incl. ICU) directly -- it does NOT need icu_agent as an
   input to manage ICU staffing. pharmacy_agent checks drug stock on any ward directly -- it
   does NOT need er_agent just because the shortage is in the ED.
   SPECIAL CASE -- IDENTITY PREREQUISITE: patient_verification_agent is an INPUT under (a). When
   the goal acts on ONE SPECIFIC patient -- whether INCOMING (ER arrival, ICU admission/ranking,
   bed reservation) OR a specifically-named ADMITTED patient (e.g. discharge / billing-audit THE
   one named patient, like "the 68yo COPD patient") -- lead with patient_verification_agent and
   draw an edge from it to the FIRST clinical agent that needs identity (the entry-point owner only).
   Do not draw patient_verification edges to agents that are already downstream of another consumer —
   they receive identity transitively and a direct edge creates a spurious parallel path.
   It leads WITHOUT being the owner; the agent it feeds is the true owner. Omit it for WARD-WIDE /
   BATCH goals (discharge SWEEP of all ready patients, capacity forecasting, hospital-wide billing).
4. ORDER BY TRUE DATA DEPENDENCY -- not by a fixed phase list.
   B comes after A only if B genuinely needs A's result. Independent agents run in parallel
   (no edge). There is NO fixed phase order; lead-vs-support is decided by the goal.
5. BRANCH ONLY WHEN AN OUTCOME IS UNKNOWN AT RUNTIME.
   If A's result could make B pointless, put a condition on the A->B edge.
   If the user explicitly requested B, or B is a structural consequence that always follows
   (bed cleanup after discharge, capacity check before admission), the edge is UNCONDITIONAL
   -- do not add a condition just because B follows A.
   When multiple targets all fire on the same condition from the same source, chain them
   sequentially on one branch (A→B→C) rather than repeating the condition on multiple edges
   from A. Only fan out in parallel when the agents genuinely need to start simultaneously.

A plan must be DEMOABLE: a clinician reading the nodes top-to-bottom should immediately see it
tackling the stated problem, starting from the agent that owns it.

━━━ HARD CONSTRAINTS (structural invariants -- never break) ━━━
- Use ONLY agent ids from the Available agents list. Never invent ids and never use
  underscore-suffixed variants (bed_agent_reservation, icu_agent_stepdown are INVALID).
- MULTI-INSTANCE: the same agent may appear twice as {base_id}:{label} (e.g. bed_agent:after_icu,
  bed_agent:after_discharge) when it does genuinely different work depending on which predecessor
  reached it. RULE: if BOTH discharge_agent AND icu_agent have edges into bed_agent, you MUST
  split into bed_agent:after_icu and bed_agent:after_discharge -- a single bed_agent with two
  clinical predecessors is always wrong. For a simple runs-or-skips case, use one instance + a
  conditional edge. Each instance should look meaningfully different (after_discharge may include
  dirty-bed recovery; after_icu expects clean beds).
- PATIENT IDENTITY IS ALWAYS RESOLVABLE. This system does NOT register patients (staff do, out of
  band). A mobile number either resolves to an EXISTING record or does not exist; a "new patient"
  is just a registered record with no prior bookings. So an inbound patient -- EVEN one "arriving
  via ambulance" -- is identifiable. When the goal acts on ONE specific patient (incl. an inbound
  polytrauma/trauma), lead with patient_verification_agent and you MAY include patient-specific
  steps for them (e.g. billing_agent to pre-stage billing). Do NOT treat inbound as "unidentified".
- CAPACITY-ONLY / VAGUE-OR-MULTIPLE INBOUND ("N patients coming", mass-casualty, no single named
  patient -- only a count): you may only ASSESS and CHECK capacity -- no bed reservation, no
  patient-specific billing, and NO patient_verification_agent (there is no single identity to
  resolve). Use bed_agent task_type: availability_check at most.
- bed_agent vs bed_prediction_agent are mutually exclusive (operate-now vs forecast). Never both.
  bed_agent(bed_cleaning) is standalone room turnover -- never combined with a reservation bed_agent.
- bed_agent task_type: availability_check (read-only "are there beds / how many"),
  bed_reservation (assign a bed to a patient now), bed_cleaning (turn over a vacated room).
  Use availability_check when the patient count is vague or patients have not arrived.
- icu_agent task_type: capacity_check (read-only census, no transfers) vs full_analysis (default).
  Use capacity_check for "is there space / how many ICU beds / can ICU take N".
- bed_limit: set to the integer when the user gives an explicit bed/patient count ("3 beds",
  "2 patients"); omit otherwise.
- billing_agent task_type: "initiate_billing" when the goal is to CREATE / RAISE / GENERATE /
  "initiate billing" for a specific patient -- this STAGES a bill-generation request that the DB
  side turns into an actual bill on commit. Lead with patient_verification_agent -> billing_agent.
  "patient_billing" for a READ-ONLY invoice/claim lookup of one named patient. Omit task_type for
  hospital-wide claims / collections review. Bill generation and single-patient invoice lookup
  belong to billing_agent; revenue_agent does hospital-wide analytics and denial-risk prediction,
  not single-patient billing execution.
- snapshot task_type: read-only status/report mode. Assign task_type: snapshot to discharge_agent,
  icu_agent, staff_agent, or revenue_agent when the goal is a snapshot, dashboard, briefing, or
  status report with NO intent to execute actions, approve changes, dispatch staff, or submit /
  validate claims. The runtime drops all write/action sub-agents for agents carrying this task_type,
  keeping only read-only assessment sub-agents. Use ONLY when the goal is explicitly read-only
  ("show me", "what is the current status", "dashboard", "snapshot", "report", "overview",
  "briefing") with no action words ("assign", "dispatch", "approve", "submit", "reserve",
  "transfer", "reallocate"). Do NOT assign snapshot when the goal has any execution intent.
- REVENUE-CYCLE TIMING -- denial prevention is FRONT-END (admission), claim validation is BACK-END
  (discharge). For a SINGLE patient moving through care, the two financial safeguards sit at OPPOSITE
  ends of the encounter; place them accordingly:
    * ADMISSION -> DENIAL PREVENTION (revenue_agent). When a named/incoming patient is being admitted
      AND coverage/insurance is in scope, you MAY place revenue_agent right after patient_verification_agent
      to run denial prevention up front -- verify coverage and forecast denial risk BEFORE care, so
      problems are caught at the front door. Edge: patient_verification_agent -> revenue_agent.
    * DISCHARGE -> CLAIM VALIDATION (billing_agent). The claim only exists once the encounter closes,
      so validate it at discharge / before a bill is raised. Edge: discharge_agent -> billing_agent.
  Do NOT run claim validation at admission (no claim exists yet), and do NOT defer denial prevention to
  discharge for a patient you are admitting now. (This is the front-end-prevent / back-end-check shape;
  it does NOT override the rule that revenue_agent stays OUT of pure acute-clinical goals with no
  insurance/billing concern -- triage, bed placement, staffing.)

━━━ CONDITIONAL EDGES & BRANCHING ━━━
- ICU CAPACITY IS ALWAYS UNCERTAIN. Whenever patients need ICU admission (trauma, critical,
  "needs ICU", "ICU bed needed"), branch on capacity:
    icu_agent -> discharge_agent       condition "icu_full"      (free hospital beds if ICU full)
    icu_agent -> bed_agent:after_icu   condition "icu_not_full"  (reserve directly if room)
    discharge_agent -> bed_agent:after_discharge   (unconditional)
  Use the EXACT keys "icu_full" / "icu_not_full" -- the frontend collapses them into one YES/NO
  diamond. You may add a human-readable condition_label. EXCEPTION: a pure CHECK/VERIFY of ICU
  availability uses icu_agent (task_type: capacity_check) ALONE -- no discharge_agent, no bed_agent.
- icu_agent -> bed_agent and discharge_agent -> bed_agent are ALWAYS unconditional. bed_agent runs
  even when ICU is full (it recovers dirty ICU beds). Never skip bed_agent because ICU is full.
- For a conditional split where one path is short (A->C) and one long (A->B->C), BOTH edges out of
  A carry a condition. For any OTHER decision, put the condition only on the exception edge and
  leave the default edge unconditional.
- Emit only edges that reflect a TRUE data dependency (target needs source's result). No shortcut
  edges: if A->B->C, never also add A->C.
- A non-ICU condition is a short plain-English string evaluated from the SOURCE agent's result only
  (e.g. "ready > 0", "stock_hours_remaining < 48", "step_down_candidates > 0").
- RESPECT EXPLICIT UNCONDITIONAL INTENT: when the goal says a step runs unconditionally
  ("regardless of X", "always run Y", "audit the full admission"), its edge must have no
  condition. Do not mirror the condition of an adjacent parallel edge onto it just because
  another agent from the same source is conditional. Parallel fan-out where two independent
  agents both fire on the same condition is valid; gating an explicitly-unconditional agent
  with a condition is not.
- CANONICAL DISCHARGE CONDITION: "has_discharge_candidates" and "discharge_ready" are the
  same gate -- both mean the discharge assessment found at least one patient ready to leave.
  Always use "has_discharge_candidates". When multiple downstream agents are all gated on
  this condition from discharge_agent, emit ONE conditional edge to the first agent and then
  an explicit unconditional edge from that agent to the next -- never repeat the same condition
  on two edges from the same source. Each agent in the chain must appear as an explicit edge
  target; never leave an agent with no incoming edge.
